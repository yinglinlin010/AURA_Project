# AURA Frontend Architecture (Current Web Simulator)

## Scope and current status

`apps/web-simulator` is a Vite + React visual simulator. [`src/App.tsx`](../../apps/web-simulator/src/App.tsx) renders the five Section 64 role previews: Cluster, Center, Front Passenger, Rear, and Interactive Window. A separate Developer Control Console sits outside those display previews. The five compositions are visual references in one browser page, not five independent HMI clients or proof that five physical displays are connected. The final visual authority remains Section 64 of [`AURA_MASTER_SPEC_2026-10-02.md`](../product/AURA_MASTER_SPEC_2026-10-02.md) and the supplied [`AURA_UI_UX_Handoff/`](../../AURA_UI_UX_Handoff/).

Five logical Gateway sockets are opened from this one browser page using the enabled registry identities `cluster-main` / `main-computer` / `cluster`, `center-main` / `main-computer` / `center`, `front-passenger-main` / `main-computer` / `front_passenger`, `rear-tablet` / `rear-tablet-device` / `rear`, and `window-tablet` / `rear-tablet-device` / `interactive_window`. Each socket registers independently with its exact device/display pair and has its own Gateway connection state. These are five logical registrations in one browser simulation, not five independent physical displays or hardware clients.

## Gateway connection and shared state

The hook is [`apps/web-simulator/src/core/useAuraCommand.ts`](../../apps/web-simulator/src/core/useAuraCommand.ts). It uses `VITE_AURA_WS_URL`, or the page host with `VITE_AURA_WS_PORT` (default `8080`) and `/ws`. Client registration uses protocol version 1. Commands use the protocol's nested shape: `{ kind: "command", envelope: { ... , sender, command } }`; the sender display/device identity and runtime session ID must match the connection.

All five sockets consume Gateway snapshots and shared events into the same browser-visible state; each exposes its own connecting, connected, error, or disconnected status. The Cluster speed and Control Console display use shared vehicle state, while driver cognitive-load reports update shared load state. The Control Console sends `vehicle.telemetry.report` and `driver.cognitive_load.report` through the Center registration and lists all five logical socket states with device and role.

The Developer Control Console's four load buttons send simulated `low`, `normal`, `high`, or `critical` reports; they are not sensor evidence. At high load, Center hides proposal details and shows the silent orange edge marker only while a shared proposal is `deferred`; Cluster is unchanged and passenger status remains shared. Center restores proposal details and consent controls only after a shared proposal status is `awaiting_consent` and load is authoritatively `low` or `normal`.

At critical load, Cluster continues to show its existing vehicle state, including speed, and Center retains its route summary and map while suppressing proposal details, the journey ledger, and non-essential Center controls. The protocol has `safety.override.activated` and `safety.warning.cleared` event shapes, and the reducer stores active warning state. The runtime currently has no evidenced producer for the matching clear event, so the end-to-end clear lifecycle and rendered restoration behavior remain incomplete. These simulated load inputs are not hazard evidence. No runtime/browser visual validation was performed for these transitions.

The Front Passenger **Propose stop** interaction sends `action.propose` for `ADD_TRIP_STOP`, with `targetRole: "center"`, `priority: "secondary"`, and `requiresConsent: true`. The proposal ID, place label, and category are carried in the nested proposal request. Center renders proposal status from gateway snapshots/events and sends `action.consent` with `approve` or `decline` over its own registered connection. Deferred state and release after driver load falls are rendered from shared proposal status/reason events. An accepted `journey.stop.added` event adds the stop to the visible Center journey; the UI does not treat a click or command send as acceptance.

Connection, registration, receipt, and gateway error feedback are surfaced for all five logical registrations; per-display status is visible beside each preview and in the external Developer Control Console. Proposal and consent continue to use the Front Passenger and Center registrations. An acknowledgement alone represents command receipt and is not proof of completed domain work.

## Center browser voice path

The simulator header's Center voice control starts a user-initiated browser capture flow through the Center gateway connection. The browser requests microphone permission, then uses an `AudioWorklet` processor to mix/resample to mono 16 kHz and encode signed 16-bit little-endian PCM. It sends `voice.start` / `voice.stop` protocol messages and binary PCM frames to the Gateway. The UI consumes `voice.status`, `voice.transcript`, `error`, and `voice.audio` markers, shows input/output transcript and error feedback, and plays returned provider PCM in the browser. Microphone access requires browser support for `getUserMedia`, `AudioContext`, and `AudioWorklet` in a secure context.

The host constructs a Voice Runtime and supports mock speech, explicitly configured Gemini Live, or explicitly configured local Whisper. Local Whisper invokes whisper.cpp and macOS speech utilities; its generated-audio smoke is not live browser capture evidence. This is a browser simulator integration, not validated vehicle microphone/speaker integration, wake-word detection, cabin-noise behavior, or latency. The Center microphone feature does not implement camera/perception.

## Preview boundaries

The five display layouts and static route/place/weather details remain illustrative where not explicitly driven by shared gateway state. Rear and Interactive Window controls are local preview state even though their logical sockets consume shared Gateway snapshots/events. Do not represent their content as live provider data or the five registrations as physical-client evidence.

The host's `Gemma2BOfflineSimulator` is deterministic text matching, not local model inference; optional Ollama proposal inference is a separate path. Connectivity state, offline routing/fallback, a configurable HTTP health probe, and simulated recovery are implemented, but do not establish durable task recovery or live provider/network recovery. Core Host conditionally constructs Mapbox search/routing adapters and a Journey store when configured, and the Gateway has search and route-preview paths. Provider success, complete recommendation ranking, and the static preview content are not established as live provider data.

Styling lives in [`apps/web-simulator/src/App.css`](../../apps/web-simulator/src/App.css) and [`apps/web-simulator/src/index.css`](../../apps/web-simulator/src/index.css). The backend registration and protocol sources are [`apps/core-host/src/main.ts`](../../apps/core-host/src/main.ts), [`apps/core-host/src/hmi-gateway.ts`](../../apps/core-host/src/hmi-gateway.ts), and [`apps/core-host/config/display-registry.json`](../../apps/core-host/config/display-registry.json).
