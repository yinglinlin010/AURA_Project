**Scope and evidence rule:** This file audits repository source and documentation only. “Source present” means static implementation evidence, never successful runtime behavior. Static scenario means a scenario definition exists, not that it ran. Runtime, device, provider, model, benchmark and live-demo evidence is reported separately; none is inferred from source presence. No tests/build/browser/provider/model/device execution was performed for this audit.

Evidence references use repository-relative paths and source line anchors (`#Lx`). Master Spec requirements are cited by section and line. Where a requirement needs observation, the row names concrete acceptance evidence that remains due.

## Status vocabulary

- **Source present — unverified:** relevant source path/control flow is present; no runtime pass is claimed.
- **Partial:** some requirement elements exist, while stated elements/evidence remain missing.
- **Not evidenced:** no qualifying implementation or proof was found in the inspected paths; next evidence is specified.
- **V1 excluded:** Master Spec explicitly places it outside Competition V1.
- **Pending human gate:** only an authorized human may decide the required data/rights review; repository state is not approval.

### Safety warning lifecycle: current behavior and unresolved semantics

Critical typed signals enter `CoreRuntime.ingestSignal`, emit `context.signal.received`, then the deterministic Safety Supervisor can emit `safety.override.activated` and interrupt secondary tasks [core-runtime.ts#L130-L180](../../packages/core-runtime/src/core-runtime.ts#L130), [safety-supervisor.ts#L15-L62](../../packages/core-domain/src/safety-supervisor.ts#L15). Reducer stores a shared active warning; a matching supervisor clear event can clear it [reducer.ts#L112-L124](../../packages/core-domain/src/reducer.ts#L112). Center/Cluster consume shared warning state [App.tsx#L177-L179](../../apps/web-simulator/src/App.tsx#L177); static scenario covers critical activation/persistence [critical-warning-persistence.yaml#L1-L19](../../scenarios/safety/critical-warning-persistence.yaml#L1). Generic model/provider proposals reject WARN and urgent priority [action-gate.ts#L29-L41](../../packages/core-domain/src/action-gate.ts#L29), so they cannot activate/clear supervisor warnings.

The implementation decision is intentionally conservative: no acknowledge/dismiss control or automatic clear source is inferred. [SAFETY_WARNING_LIFECYCLE.md#L26-L40](SAFETY_WARNING_LIFECYCLE.md#L26) records that spec §§61/64 do not define whether sensor-clear, acknowledgement, replacement by a later warning, or immediate HMI restoration is correct. Current reducer retains the first active warning until a matching clear event; runtime emits activation but no clear command/event path is evidenced. **Open product decision:** define authorized clear condition, whether acknowledgement is permitted, replacement/priority rules for a second critical warning, and HMI restoration behavior. Until resolved, test activation/persistence/ordinary-content suppression only; do not claim a complete clear lifecycle.
